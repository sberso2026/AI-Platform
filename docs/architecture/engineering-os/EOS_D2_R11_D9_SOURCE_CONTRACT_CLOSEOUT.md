The payload uses the architecture source-contract field list: object identity, object type, exact revision, currentness, authority, provenance, requirements, assumptions, decisions, evidence, interfaces, spatial context, maturity, limitations, and canonical fingerprint. ## Exact source binding

Every contract binds a Civil object id to that object's fingerprint. A floating label such as latest is rejected. A contract recorded against one revision stays on that revision. A later successor revision requires its own contract. The earlier contract is not rewritten and is not repointed.

## Payload

The contract exposes the object identity, type, exact revision, tenant, workspace, project, lifecycle maturity, currentness, supersession state, authority, and provenance. It copies requirements, assumptions, and decisions that explicitly name the object. It copies evidence identifiers those records and explicit supported-by lineage already cite. It copies spatial references, surfaces, and grading context through stored identifiers, and it leaves roads, drainage, and utility sections empty when no stored identifier applies. It copies interface, review, validation, and explicit lineage records that cite the same revision. It does not derive a new engineering fact.

## Authority

The recorded authority remains the Civil context authority. The contract does not transfer that authority. Future D9 consumption does not make D9 the Civil engineering authority. An AI actor and an administrator cannot issue the contract.

## Currentness and limitations

The fresh projection uses the latest explicit currentness mark for that exact revision, or the object record status when no mark exists. A stale revision cannot be issued as current. A reassessment-required revision is not represented as validated. Known handoff, review, and validation limitations are copied into the contract. A standing limitation states that the contract does not transfer authority, start D9, validate, approve, certify, or conform Civil engineering. An earlier contract keeps the currentness it recorded. A later contract records the later state. Neither contract is silently mutated.

## Review and validation

Review state stays REQUESTED and is not engineering validation. A validation record may still say VALIDATED for the revision it cites, and that state remains not conformant, not approved, and not certified. When the revision is reassessment-required, the contract does not represent that validation as the current validated state. Review and validation are not copied onto a successor revision.

## Interfaces and spatial lineage

An awaiting-counterpart handoff stays incomplete and keeps a null counterpart. A stale handoff stays stale. A currentness mark can show a handoff as stale in a new contract while the historical handoff record keeps the source revision it cited. Lineage entries are the stored edges that touch the exact object revision. A candidate edge remains non-authoritative. Inferred, proximity, similar-name, and chronology lineage is rejected.

## Fingerprint, history, and scope

The same governed state produces the same canonical fingerprint. Replay of the same contract id and fingerprint returns the existing record. A conflicting fingerprint or a cross-scope actor is rejected. History is append-only. Issuing a contract does not change object fingerprints, requirement text, handoff source revisions, or validation subject revisions.
