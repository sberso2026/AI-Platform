Post-D1J canonical roadmap

This is a new roadmap governance decision. The phase identifier EOS-D1K-0-CROSS-DISCIPLINE-STRUCTURAL-INTERFACES-ARCHITECTURE did not exist in the repository before this decision. This document records the route after EOS-D1J-R5-STRUCTURAL-OPTIMIZATION-CERTIFICATION-CLOSEOUT. Earlier roadmap documents, including the post-D1I canonical roadmap, remain historical records and are not rewritten.

EOS-D1J-R5-STRUCTURAL-OPTIMIZATION-CERTIFICATION-CLOSEOUT remains the D1J closeout. D1J status remains COMPLETE_BOUNDED_WITH_LIMITATIONS. D1J maturity remains STRUCTURAL_OPTIMIZATION_CERTIFICATION_BOUNDED_RUNTIME_IMPLEMENTED. That maturity does not mean an optimizer, a search, candidate generation, live solver optimization, model mutation, engineer validation, conformance validation, or certification eligibility. Certification eligibility remains NOT_ELIGIBLE. D1G remains NOT_CERTIFIED. Concrete parameter semantics remain NOT_AVAILABLE. This decision does not promote D1J optimizer runtime, solver runtime, model mutation, engineer validation, conformance validation, or certification eligibility.

Authoritative roadmap

The reused current statement is the D1J closeout. It required a separate roadmap governance decision and did not authorize a successor. The post-D1I roadmap remains the historical decision that authorized D1J architecture. Its next-phase constant stays the D1J architecture phase. This decision adds a new post-D1J roadmap rather than rewriting that history. No parallel capability manifest is created. D1K runtime is not marked implemented.

D1K identity

The canonical D1K name remains CROSS-DISCIPLINE STRUCTURAL INTERFACES. D1K runtime remains NOT_STARTED. The completion plan describes D1K as populating the existing D0 cross-discipline interface contract with structural object and evidence references. Recorded dependencies are D1A and D1F. D1K does not depend on D1J runtime. Risk D0-R04 says D1K declares structural interfaces only and cycle detection remains D9. The same plan lists piping, mechanical, process, electrical, geotechnical, and civil exchanges as declared sink and source interfaces. AI impact stays advisory. D1F already records future discipline seams and leaves integrated orchestration to D1K without starting D2 through D9.

An interface record is not another discipline's calculation, not engineering approval, and not D9 cross-discipline intelligence. An interface handoff is not engineering approval. Interface compatibility is not global cross-discipline intelligence.

Architecture and runtime

D1K architecture can be defined before D2 through D8 runtime exists. The D0 discipline identities already name structural, civil, geotechnical, mechanical, piping, process, electrical, and instrumentation and control. The D0 interface contract already carries interface identity, relation, source discipline, target discipline, source object, target object, evidence, declared or active or retired status, provenance, and a human-review requirement. D1A and D1F already supply structural target identity. Defining architecture on those contracts does not implement civil, geotechnical, mechanical, piping, process, electrical, or instrumentation and control engineering, and it does not implement D9.

Architecture readiness, reference-runtime readiness, external-reference readiness, internal-discipline integration readiness, and cross-discipline intelligence readiness are separate. All remain false. This decision authorizes only the architecture definition. It does not authorize interface runtime, compatibility runtime, cross-discipline calculation, cycle detection, or D9 runtime.

A later bounded reference runtime could record a human-authored interface, a governed imported interface, or an external-system reference without a full D2 through D8 pack. That runtime is not authorized now. Live internal EOS-to-EOS integration cannot exist until the counterparty pack exposes a canonical source contract. Those packs remain planned.

Interface architecture

D1K-0 must reuse the D0 interface contract and extend it with project scope, the structural target, direction expressed by source, target, and the existing relation allowlist, semantic and schema identity, an exact source reference, the receiving target, authority, validation, applicability, requiredness, fingerprint, and append-only history. Free-form discipline names are not governing identity. A second structural asset identity is not planned. Source-domain authority stays with the source. Registering an interface does not promote that authority. Accepting an interface does not promote engineering validation.

Direction does not invent inbound, outbound, or bidirectional tokens. The repository already governs relations such as provides input, requires input, load transfer, data dependency, design-change impact, interface requirement, review required, and assumption dependency. A bidirectional exchange exists only when an explicit governed relation says so.

Units reuse the existing EOS unit system. No parallel unit system is planned. Silent unit conversion is not planned. Where a spatial or vector quantity is exchanged, coordinate-system identity is explicit and is not inferred from geometry. Where a load, reaction, or vector quantity is exchanged, axis and sign convention identity is explicit and is not inferred from numeric values.

The semantic and schema registry is allowlisted. Arbitrary caller JSON is not governed engineering truth. No generic payload engine is planned. A future record prefers an exact reference or projection. Uncontrolled copying of a source engineering body is not planned. The source identifier latest is not allowed. A source change marks the dependent interface record stale and does not mutate the upstream source. Provenance reuses the digital thread. No parallel digital thread is planned. Fingerprints reuse the existing canonical fingerprint for the interface definition, the source reference, the semantic or schema identity, the compatibility state, and any handoff or review state.

Requirement meanings stay distinct: required input, provided input, requested output, provided output, acknowledged handoff, and unresolved interface. D0 status is not engineering approval. A closed interface is not design approval. Review reuses the existing engineering-review decision workflow. No second approval engine is planned.

Diagnostics may represent missing information, semantic incompatibility, unit mismatch, coordinate mismatch, axis or sign mismatch, version mismatch, a stale source, insufficient authority, and a pending counterparty response. A mismatch is not a structural failure. Diagnostics do not automatically resolve an engineering conflict. AI cannot reconcile that conflict, invent an engineering input, invent a counterparty response, change source authority, or approve an interface. AI may summarize an interface, identify a missing input, explain a mismatch, draft a query, and highlight a stale reference.

Ownership boundaries

D1K does not re-author D2 civil, D3 geotechnical, D4 mechanical, D5 piping, D6 process, D7 electrical, or D8 instrumentation and control engineering. It does not start those runtimes. It does not start D9. It does not move cycle detection out of D9. It does not authorize cross-discipline optimization or a global consistency solver. It does not add an engineering formula, a structural check engine, or another discipline's check engine. It does not absorb D1M CAD or BIM intelligence or D1N concept-to-detailed orchestration.

D1L Structural Global Certification Gate remains NOT_STARTED. It still depends on the earlier in-scope structural tracks, including design-check evidence. The completion plan also assigns it consequence classes, pack maturity, and an EU or global check without an EU-only claim. A future D1L may require exact D1K interface evidence when a cross-discipline input affects a structural certification claim. Interface acceptance is not that gate. This decision does not start D1L.

D9 may later consume governed D1K interface references and states for cross-discipline intelligence and cycle detection. D1K does not implement that consumption.

Discipline order remains D1 structural, D2 civil, D3 geotechnical, D4 mechanical, D5 piping, D6 process, D7 electrical, D8 instrumentation and control, and D9 cross-discipline intelligence. D2 through D9 are not started. The D1 structural pack is not complete. No database migration is required.
