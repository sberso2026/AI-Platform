# EOS-D6-0 Process Architecture

## Purpose

D6 is the Process engineering discipline inside Engineering OS. Phase EOS-D6-0-PROCESS-ARCHITECTURE-CANONICALIZATION defines Process scope, ownership, the canonical object taxonomy, Process truth and evidence boundaries, identity and revision rules, currentness, requirements and change governance, discipline interfaces, future review and validation governance, the future D9 source contract, and the later implementation sequence. It does not record a Process object and it does not calculate a balance, a duty, a relief load, or a hydraulic result.

The Piping track remains complete with the classification COMPLETE_BOUNDED_WITH_LIMITATIONS and a runtime count of eleven. Mechanical, Civil, and Geotechnical remain complete with the same classification. This phase does not reopen D1, D2, D3, D4, or D5. D1 structural pack complete remains no. D1N stays closed. D6 runtime stays at zero. D7, D8, and D9 stay unstarted.

## Ownership

D6 owns bounded Process engineering context and governed Process evidence for plant and project process systems that the canonical project assigns to Process. That includes process systems, process units, streams, fluid and service context, phase and composition context, operating cases, design cases, Process-source conditions, the process design basis, requirements, assumptions, engineering decisions, utility and process service context, mass-balance and energy-balance evidence, hydraulic and other explicitly supplied calculation evidence, equipment duty and performance requirements, relief, depressuring, and process-safety scenario context, control intent and measurement requirements, process diagram and document evidence, discipline interfaces, review and validation requirements, currentness, lineage, and a future D9 source contract.

Governed context and evidence are not calculation runtime. Naming a stream, a duty, a relief case, or a balance document does not calculate, redesign, validate, or approve it.

## Scope

In scope are plant and project process systems and Process-owned records covered by the canonical project Process discipline.

Not in scope are Piping line design, Mechanical equipment design, Electrical design, Instrumentation and Control design, Structural engineering, Civil engineering, Geotechnical engineering, functional-safety validation, and multidisciplinary reasoning. D6 does not absorb D1 through D5, D7, D8, or D9.

## Object taxonomy

Adopted object types are PROCESS_SYSTEM, PROCESS_UNIT, PROCESS_STREAM, PROCESS_SERVICE, PROCESS_FLUID, PROCESS_COMPOSITION_CONTEXT, PROCESS_OPERATING_CASE, PROCESS_DESIGN_CASE, PROCESS_CONDITION, PROCESS_DESIGN_BASIS, PROCESS_CALCULATION_EVIDENCE, PROCESS_EQUIPMENT_DUTY, PROCESS_UTILITY_REQUIREMENT, PROCESS_RELIEF_SCENARIO, PROCESS_SAFETY_CONTEXT, PROCESS_CONTROL_INTENT, PROCESS_MEASUREMENT_REQUIREMENT, PROCESS_DOCUMENT_EVIDENCE, PROCESS_INTERFACE, and PROCESS_GOVERNANCE_RECORD.

Process area is the same concept as process unit and is not a second object type. Process phase is a classification on fluid or composition context, not an object type. Vapor, liquid, two-phase, solid, and mixed are those classifications. Mass balance, energy balance, hydraulic, pressure drop, heat duty, equipment duty, relief load, depressuring, utility consumption, and other process calculations are evidence classes under process calculation evidence. They are not separate authoritative object types and they are not calculations performed by D6-0. Depressuring is a relief-scenario class, not a second scenario object. Requirement, assumption, engineering decision, and evidence reference are governed record types beside the taxonomy. Review and validation context is a governance record, not a second identity model.

An unknown or freeform type does not become authoritative by being named. Authoritative object types are allowlisted.

## Process and Piping

A process stream is not a piping line. Stream identity is not line identity. A future explicit reference from a process stream to an exact D5 line is allowed. That reference does not transfer D5 authority and does not infer D5 line membership from the stream identity. A process service is not a piping service context and does not auto-create a D5 piping service. A process condition is not a piping design condition. A process-source condition is not an adopted piping design condition. D6 does not create a D5 adopted piping design condition. D5 remains responsible for any explicit governed adoption. The D6 to D5 interface uses the existing D5-R8 future contract subjects and does not replace that contract.

## Process and Mechanical

A process equipment duty is not mechanical equipment design. A process equipment requirement is not a validated mechanical selection. D6 does not transfer mechanical authority and does not validate D4 engineering. The interface reuses the existing D4 future process contract subjects and adds utility requirement and process-side package requirement as Process-side extensions. Runtime integration remains zero.

## Process, Electrical, and I&C

Process control intent is not instrumentation and control design. A process measurement requirement is not instrument design. A setpoint context is not a validated control configuration. A process electrical requirement context is not electrical design. D6 does not transfer electrical authority or I&C authority. Future D7 subjects are motor or load process requirements, power requirement context, and utility power process context. Future D8 subjects are control intent, measurement requirements, alarm or trip process intent, setpoint source context, control-valve process requirements, and process safeguarding requirements. D7 and D8 runtime stay unstarted. Integration counts stay zero.

## Structural, Civil, and Geotechnical

No direct D6 interface to D1, D2, or D3 is defined. Existing architecture does not justify one. Direct authority transfer is not allowed. D6 does not validate D1, D2, or D3 engineering.

## Calculation and evidence

D6 may later hold governed external or explicitly supplied calculation evidence. D6-0 performs none of those calculations. Calculation evidence is not a validated process design and is not code conformance. Pipe sizing remains outside D6. Mass balance, energy balance, hydraulic, pressure drop, equipment duty, relief, depressuring, and utility calculation runtime counts are zero. Automatic process calculation, automatic redesign, automatic validation, conformance, approval, and certification counts are zero.

## Process safety and relief

D6 may own process-side relief scenarios, initiating cases, required relief load context, depressuring requirements, process safeguarding requirements, and hazard-study evidence references. A relief scenario is not relief-device design. A relief requirement is not a validated relief-device selection. A hazard finding is not an approved safeguard. Process-safety context is not functional-safety validation. D8 keeps future functional-safety authority.

## Documents

PFD references, heat and material balance documents, process datasheets, design-basis documents, P&ID process-context references, calculation reports, and vendor or process evidence are document kinds. A process document is not process identity. A process diagram is not a validated process design. Documents are evidence and context.

## Identity, currentness, and lineage

Identity, currentness, digital thread, fingerprint, and maturity reuse the canonical EOS mechanisms already used by D5. No parallel identity system, currentness engine, digital thread, fingerprint algorithm, maturity enum, requirement engine, assumption engine, decision engine, or change engine is created. An exact revision reference is required. A floating authoritative reference is not allowed. Explicit lineage is required. Lineage is not inferred from names, tags, document adjacency, semantic similarity, or AI reasoning. Historical references are not auto-repointed. Future D6 revisions participate in the existing digital thread by exact revision, canonical currentness, and the canonical fingerprint.

## Requirements, assumptions, decisions, and change

Requirement, assumption, decision, and change governance are reused. A source requirement is not an adopted process requirement. An assumption is not a validated fact. An AI recommendation is not a process engineering decision.

## Review and validation

Review governance and validation governance are defined for a later phase. No review or validation runtime exists in D6-0. A reviewed process record is not a validated process record. A validated process record is not conformant, approved, or certified. AI and admin are not process engineering authority and are not process reviewer authority.

## D9 source contract

The future source contract may expose existing process identities, systems, streams, services, cases, conditions, fluid and composition context, requirements, assumptions, decisions, evidence, equipment duties, process-safety and relief context, interfaces, review and validation state, currentness, explicit lineage, applicability, limitations, provenance, authority, and fingerprint. It exposes existing truth only. It does not create a fact or transfer authority. The source-contract runtime count is zero. D9 integration is zero. D9 runtime remains unstarted at count zero. Cross-discipline reasoning, conflict detection, conflict resolution, and recommendation remain zero. D9 owns future global multidisciplinary reasoning.

## Scope and security

Tenant, workspace, and project scope is part of the architecture. Cross-tenant D6 access is not allowed. Least privilege, provenance, auditability, exact revisions, and immutable history apply. No silent authority promotion is allowed. No new jurisdiction profile is added. No legal or regulatory compliance is claimed. D6 is not engineering-validated, conformant, approved, certified, or generally available.

## Phase decomposition

The later D6 sequence has twelve phases. The count is the length of that sequence. The subjects do not copy the Piping phase names. They follow the Process boundaries in this architecture, one primary subject each, with no overlapping authority:

1. EOS-D6-R1-PROCESS-IDENTITY-AND-OBJECT-FOUNDATION, type PROCESS_IDENTITY_AND_OBJECT_FOUNDATION. Identity and the allowlisted object taxonomy only.
2. EOS-D6-R2-PROCESS-SYSTEM-STREAM-AND-SERVICE-CONTEXT, type PROCESS_SYSTEM_STREAM_AND_SERVICE_CONTEXT. Systems, units, streams, fluids, and services. Stream is not a piping line.
3. EOS-D6-R3-OPERATING-AND-DESIGN-BASIS-AND-CONDITIONS, type OPERATING_AND_DESIGN_BASIS_AND_CONDITIONS. Operating cases, design cases, Process-source conditions, and design basis. These are not adopted piping design conditions.
4. EOS-D6-R4-PROCESS-EVIDENCE-AND-BALANCES, type PROCESS_EVIDENCE_AND_BALANCES. Governed calculation evidence and document evidence. No calculation is performed.
5. EOS-D6-R5-EQUIPMENT-DUTY-AND-UTILITY-CONTEXT, type EQUIPMENT_DUTY_AND_UTILITY_CONTEXT. Process duty and utility requirements. These are not mechanical design.
6. EOS-D6-R6-PROCESS-SAFETY-AND-RELIEF-CONTEXT, type PROCESS_SAFETY_AND_RELIEF_CONTEXT. Process-side relief, depressuring, and safeguarding context. This is not device design or functional-safety validation.
7. EOS-D6-R7-REQUIREMENTS-ASSUMPTIONS-AND-CHANGE, type REQUIREMENTS_ASSUMPTIONS_AND_CHANGE. Canonical requirement, assumption, decision, and change records.
8. EOS-D6-R8-DISCIPLINE-INTERFACES-AND-HANDOFFS, type DISCIPLINE_INTERFACES_AND_HANDOFFS. Bounded D4, D5, D7, and D8 handoffs without authority transfer.
9. EOS-D6-R9-REVIEW-AND-VALIDATION-GOVERNANCE, type REVIEW_AND_VALIDATION_GOVERNANCE. Review and validation state for an exact revision.
10. EOS-D6-R10-CURRENTNESS-AND-DIGITAL-THREAD, type CURRENTNESS_AND_DIGITAL_THREAD. Canonical currentness, thread, fingerprint, and explicit lineage.
11. EOS-D6-R11-D9-SOURCE-CONTRACT, type D9_SOURCE_CONTRACT. Read-only exposure of existing Process truth.
12. EOS-D6-R12-PROCESS-BOUNDED-CLOSEOUT, type PROCESS_BOUNDED_CLOSEOUT. Closeout of the bounded Process track without a further substantive runtime.

The next phase is EOS-D6-R1-PROCESS-IDENTITY-AND-OBJECT-FOUNDATION. Its scope is to implement exact governed Process identities and the canonical Process object taxonomy with tenant, workspace, and project scope, lifecycle and maturity, provenance, canonical currentness, and the canonical fingerprint. It must not implement system, stream, or service technical context, operating or design conditions, calculation evidence, equipment duty, process-safety context, requirements, interfaces, review, the D9 source contract, or any Process calculation. This architecture names that phase and does not start it.
